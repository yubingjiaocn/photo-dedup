# Photo Dedup：语义选片助手 PRD

**状态**：Draft v0.1  
**日期**：2026-09-30  
**产品阶段**：本地分组、194 组语义回放、私有 Review UI 与首轮 assisted review 已完成；可学习 Review MVP 支持事件沉淀、文件训练包导出、数据 artifact 回导与 preference/exemplar shadow，Google Photos 尚未进入真实试点。  
**产品性质**：认真打磨功能与 UI 的个人产品／可分享工具，不按商业 SaaS 建设。

> 本 PRD 只描述当前产品目标和要求。实验弯路、失败路线与纠偏证据见 [`archive/VLM_EXPERIMENT_AUDIT_TRAIL.md`](archive/VLM_EXPERIMENT_AUDIT_TRAIL.md)。

## 1. 产品定义

Photo Dedup 不是另一个“找出相似照片，再让用户自己逐组挑选”的工具。

它是一套 **review-first 的语义选片助手**：先把大量照片整理为可审阅的相似组，再综合完整画面、拍摄时序和 CV 判据，为每组直接给出 shortlist、最多三个区分点，以及明确的不确定性。系统知道什么时候应该多选、什么时候应该保留不可替代瞬间，也知道什么时候必须把决定交还给用户。

### 一句话价值

> 把“翻几千张照片并逐组比较”变成“快速确认大部分可靠建议，只认真看少量真正困难的组”。

### 核心边界

- **原片安全是唯一 P0 安全目标。** 扫描、特征、VLM、UI 和测试不得修改原片内容、时间戳或目录结构。
- 产品默认只提供建议，不自动永久删除照片。
- 只有字节完全相同且满足原片身份条件的副本可以进入自动处理候选；其他相似照片保留人工确认路径。
- VLM、CV 和历史选择都不能单独获得文件操作权限。
- review 与 execute 必须分离；文件动作必须显式触发、目标可恢复，并在执行前再次核对 `file_id + content_sha256`。
- 与原片安全无直接关系的严格措辞、隐私词法、商业合规、精细成本门禁和企业级审计暂不作为开发阻塞项；它们可以记录 warning，不能拖慢核心功能与 UI 验证。

### 投入边界

以下部分按正式产品标准认真做：

- 选片建议是否真的减少人工比较；
- 完整组图、多人、动作阶段和不可替代瞬间是否看对；
- review UI 是否清楚、顺手、能快速接受或修改建议；
- 原图安全、运行恢复、身份绑定和失败提示；
- VLM 调用数、成本和结果是否对用户透明。

以下部分保持够用即可，不做商业化过度建设：

- 不做账号、订阅、支付、套餐售卖或用量结算系统；
- 不做多租户、团队空间、RBAC、审批流或企业审计平台；
- 不做 SLA、客服后台、增长埋点、营销站和插件市场；
- 不为覆盖所有硬件、云厂商和操作系统牺牲核心体验；
- 不提前建设大规模在线服务，默认仍是本地运行、用户自带模型能力。

工程优先级固定为：**原片安全 > 选片质量 > review UI > 运行效率 > 其他约束**。除原片安全外，实验阶段优先让整条流程跑通并暴露真实质量问题，不用过度防御性门禁把可审阅结果提前丢掉。

## 2. 用户问题

### 2.1 现有工具解决了一半问题

市场上常见工具通常能完成：

- 查找完全相同或视觉相似照片；
- 将连拍、重复下载和近似构图放在一起；
- 提供网格，让用户逐组手工选择。

它们减少了浏览范围，但没有显著减少判断次数。用户仍然需要决定：

- 哪张表情最好；
- 多人合照里是否所有人都状态正常；
- 动作连拍中腾空、落地、互动高潮是否都值得保留；
- 技术质量略差的照片是否拥有不可替代的叙事价值；
- 舞台、宠物、儿童、旅行打卡等场景应该看什么。

### 2.2 大图库的真实痛点

1. **选择疲劳**：相似组数量仍然很大，人工比较容易敷衍或全保留。
2. **单指标误导**：最清晰不等于最有价值；主角好看不代表其他人没有闭眼。
3. **阶段丢失**：强制单选会删掉不同动作、表情或队形的独特瞬间。
4. **黑箱不可信**：只给一个分数或“AI推荐”无法让用户快速确认。
5. **成本差异**：部分用户有充足 VLM 额度，部分用户只有有限额度或完全离线。
6. **删除风险**：错误推荐若直接执行，会造成不可逆损失。

## 3. 目标用户与运行模式

产品使用同一套本地索引、分组、证据和 review UI，通过运行模式适应不同用户，而不是维护三套产品。以下是功能模式，不是商业套餐。

### 3.1 Core：无 VLM

适合没有云模型、注重隐私或只想整理照片的用户。

提供：

- 本地扫描、可恢复增量索引和相似分组；
- 字节相同识别；
- 清晰度、曝光、脸眼、分辨率等技术提示；
- 完整组图、可信时序和人工 review；
- 本地保存用户决定。

不承诺：自动理解表情、互动、动作阶段或叙事价值。

### 3.2 Budget VLM：有限额度

适合只愿意审少量困难组或有明确预算上限的用户。

提供：

- 按组数、金额或 token 设置预算；
- 优先送入最复杂、最不确定或用户最关心的组；
- 额度用完后，其余组继续走 Core 人工 review，不降低安全性；
- 运行前显示预计组数、调用数和费用区间。

### 3.3 Full VLM：充足额度

适合大图库、希望最大化节省人工时间的用户。

提供：

- 所有疑难组各进行一次语义判断；
- 多主体、舞台、动作、互动和宠物等场景化审阅；
- 多选、不可替代瞬间、弱观察和弃权；
- 仅把低置信或冲突组留给用户重点比较。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 将用户必须逐张比较的相似组数量显著降低。
2. 在不漏掉独特阶段和互动的前提下，给出可快速确认的 shortlist。
3. 为每个建议提供最多三个具体、可见、可追溯的区分点。
4. 对多人场景检查主体集合，而不是只看最大脸或单一主角。
5. 将成本作为产品能力：支持无 VLM、有限预算和全量语义审阅。
6. 保持 review-only 与执行权限分离，确保任何推荐失败都不会直接删除照片。

### 4.2 非目标

- 不做无人值守永久删除器。
- 不做人脸身份识别、实名推断或跨相册人物画像。
- 不承诺从低分辨率或严重遮挡中恢复不存在的细节。
- 不通过旧 keeper、utility score 或用户历史选择给模型暗示“正确答案”。
- 不以模型自报 confidence、schema 通过或 fake E2E 代替真实用户验收。
- 第一版不训练个性化偏好模型；只记录用户接受、修改和拒绝，供后续分析。

## 5. 核心用户流程

### 5.1 首次运行

1. 用户选择本地照片根目录和独立输出目录。
2. 系统只读扫描照片并显示文件数、预计耗时、缓存空间和 VLM 预算预估。
3. 用户选择 Core、Budget VLM 或 Full VLM。
4. 系统完成本地特征、相似分组、可信 EXIF 时序和 review 资产。
5. 若启用 VLM，系统按相似组而非单张照片调用模型。
6. 用户进入 review workbench。

### 5.2 Review workbench

每个组必须同时展示：

- 完整组图，不允许只显示模型裁剪区域；
- 可信拍摄顺序；时间不可信时明确显示 unknown；
- AI 建议保留的照片，可为零、一张或多张；
- 最多三个区分点，并标记 high / medium / low；
- 不可替代阶段或互动（若有可靠证据）；
- CV 技术提示；
- `接受建议`、`修改选择`、`全部保留`、`稍后处理`。

低置信观察必须显示为“弱观察，不支持推荐”，不能伪装成确定事实。

### 5.3 执行

- Review 决定与文件操作分开保存。
- 默认不执行移动或删除。
- 用户明确进入执行阶段后，只能移动到可恢复位置或平台回收站。
- 执行前显示总文件数、来源、目标、空间变化和恢复方式。
- 永久删除不属于第一版产品流程。

## 6. 推荐语义

每个相似组只能产生以下一种结果：

### `select`

模型有 medium/high 证据支持至少一张建议照片。

- `recommended` 可多选；
- 多选必须说明不同照片各自保留的阶段、表情、队形或构图价值；
- 每张推荐照片至少有一条 medium/high 证据；
- low evidence 可以作为弱观察共存，但不能单独支撑推荐。

### `attention_only`

模型发现值得用户注意的差异，但不足以安全推荐。

适用于：

- 多主体覆盖不完整；
- 舞台演员过小或遮挡；
- 旁观者、镜像或反射造成歧义；
- CV 与视觉观察冲突；
- 只能形成 low-confidence 观察。

### `abstain`

输入不足、图片损坏、身份或时序不可信、组过大、模型输出无法验证，或没有可靠区分点。

弃权是正常产品结果，不是错误兜底。

## 7. 当前技术产品链

### 7.1 Production cascade：本地 student/router

生产链不把几万张原片全部发送给 VLM。全量照片先在本地完成：

- 可恢复扫描和一次解码；
- SHA、pHash、视觉 embedding、质量、曝光、脸眼、姿态和局部判据；
- 相似分组、近同质 micro-cluster、完整成员 ledger 与原图亚秒 EXIF 时序；
- 高置信 easy route：字节重复或视觉状态高度同质且质量领先明确时，本地选代表／直接进入 review；
- hard route：无法可靠区分阶段、主体、表情、构图或技术质量时，只把每个保守 micro-cluster 的代表送入 VLM；
- VLM 前生成可审计 exposure plan，逐张列出 `file_id + content_sha256`。任何 overview、contact sheet、storyboard 或 crop 含 N 张原图，都按 N 张 source exposure 计数。

开发期 VLM 是 teacher/oracle：可以完整看 development 照片，帮助提炼本地可计算 surrogate；生产期 VLM 是少量困难组的语义裁判，不是全图库预处理器。本地 router 不把 pHash、DINO、时间、姿态、脸部、表情代理或质量差距单独当偏好真值；不确定即回退到更保守 profile 或扩大 VLM 代表集合。

### 7.2 云端语义阶段

只有本地无法可靠解决的组进入一次云端 VLM 调用：

> 保守代表完整图 / 分页图 + 可信时序 + 确定性辅助视图 + L2 CV 证据 → 单次语义判断

要求：

- 完整组图始终在输入中，辅助 crop 或网格不能替代完整画面；
- 每组最多一次调用，无隐式模型升级；
- 原始请求、响应、usage、cost、hash、失败原因和 validated 结果落盘；
- 模型输出只进入独立建议 sidecar，不写 keeper 或 deletion state。

### 7.3 三张以上组的 development 候选

`large-group-v4-candidate-2` 针对 `member_count >= 3` 增加单次 JSON 内的逐帧阶段清单和可替代性分组：先覆盖每个可读表情、动作、互动或队形阶段，再在近重复阶段内选最佳代表。可看清但替代关系不确定时保守多留；视觉证据不足仍转人工。每簇代表是唯一选择依据，应用确定性生成shortlist；最多三个用户区分点不限制阶段数或保留数，全部面向用户的理由使用简体中文。

二张组默认继续使用现有 v3 选择路径；只有 versioned 本地 pair resolver 达到高置信门槛时才在 VLM 前本地选一，否则两张完整送入 v3，v3 的选择语义不变。该 resolver 只接收解码图、CV evidence 与 `file_id+content_sha256`，不得接收 group ID、旧 keeper 或标签。当前 live runner 未启用候选。二张组固定 split 为 88 组 development 与 43 组封存 holdout；开发只可读取 holdout 名字和计数。三张以上组另有 39 组 development 与 21 组 holdout。开发期不设模型费用上限；容量优化的一等指标是未来进入VLM的unique source photos，包括contact sheet内的每张原图，同时报告VLM组数、高分辨率parts和像素。任何省照片却漏掉人选或明显独特阶段的档位必须拒绝并回退。development集合一致率与容量外推不能冒充独立偏好准确率或生产实测。实现、实测和复现见 [LARGE_GROUP_TUNING.md](LARGE_GROUP_TUNING.md)。 二张组离线候选 `pair-exposure-resolver-v3 / A` 固定raw DINO≤0.045、MAE≤0.09、dHash≤8、独立来源family可用票≥6、margin≥4，仅允许local_select_one。去重质量投票后88组development为0本地、15双选组0漏保；因此当前无容量收益，本地精度无法估计。43组holdout封存，候选不接live；详细政策与证据见 [PAIR_ROUTER_TUNING.md](PAIR_ROUTER_TUNING.md)。

39组development真实单次judge实测：v4候选2完整曝光A的漏选由30降为12，但多留由14升为48，exact由15/39降至10/39；本地预筛B为149→148张曝光，漏选11、多留48、exact10/39，人选曝光召回100%。候选已锁定为实验结果，**不替换当前默认v3**；当前保守预筛仅省0.67%的输入照片，不构成显著容量突破。该实测与本地teacher replay的容量外推须分开报告。

### 7.4 本地 VLM 状态

本地 VLM 不属于当前默认链路。Qwen3-VL-8B 的 ROI 定位和场景路由实验未达到必经层门槛：存在主体截断、背景误判和高置信场景漏判。未来可继续作为可选 attention hint，但不得裁掉完整组图或控制是否进入云端。

## 8. 功能需求

### P0：首个私有可用版本

#### FR-1 本地扫描与恢复

- 同一 root/output 可安全续跑；不同 root 禁止复用同一 output。
- 原图默认只读；扫描和特征失败必须可定位到文件。
- 支持 JPEG、常见手机照片、Motion Photo 及视频保留策略。

#### FR-2 相似组与时序

- 每张组内照片使用 `file_id + content_sha256` 身份。
- 不使用 F01/F02 等展示 alias 做 join。
- 组内所有成员必须进入 coverage ledger。
- 有可信原图 EXIF 时按亚秒时间排序；mtime 不作拍摄时间。

#### FR-3 证据编译

- L0 永不进入模型；L2 只能由 L1 生成。
- embedding、base64、raw boxes/landmarks 和大数组不得进入 prompt。
- 所有判据族必须声明 exact / derived / summarized / non-evidence。
- 旧 keeper、utility 和 pair margin 不得作为模型选择证据。

#### FR-4 单次语义判断

- 支持 `select | attention_only | abstain`。
- 支持多选和最多三个区分点。
- 推荐必须绑定具体 frame 和 medium/high 证据。
- low-confidence 可显示但不能支撑推荐。
- 输出不合规时保留原始响应并安全失败，不改写成成功。

#### FR-5 Review UI

- 默认显示完整组图和模型建议。
- 超长说明折叠显示但保留原文。
- 区分“推荐依据”和“弱观察”。
- 用户可以接受、修改、全保留或跳过。
- 已保存决定可重新调整，记录 AI 接受或人工修改来源；反馈不改变保留选择。

当前已实现私有 cloud-batch review：通过显式 `--cloud-batch` + `--cloud-manifest` 加载六份只读 inventory 对应的 194 组真实结果，185 select、2 abstain、7 manual 全部展示。支持单选改多选、全部保留、稍后、逐条忽略理由与组级“不准确”反馈；五种筛选和总数/已处理/剩余进度；选择只写 `output/review-state`，重新打开可恢复。batch 或 file_id+SHA 不匹配时拒绝旧状态。预览为完整 2048 长边图片，未接执行功能。使用说明见 [VLM_REVIEW_UI.md](VLM_REVIEW_UI.md)。

#### FR-6 安全

- 原片目录在 scan、CV、VLM 和 review 阶段只读；运行前后抽样或全量核对内容 SHA，任何变化立即停止。
- 输出、缓存、缩略图、模型响应和数据库必须位于独立 output，不得写回原片目录。
- 模型、CV、缓存和 review UI 都无文件移动或删除权限。
- 执行必须是独立显式步骤；执行前重新验证 `file_id + content_sha256`，默认只移动到可恢复位置。
- 永久删除默认不实现；未来若增加，也必须是独立、二次确认且不复用 review 阶段权限。
- 非原片风险默认记录为质量 warning 或诊断信息，不作为整批测试的全局停止条件。

### P1：可分享版本

- VLM 预算：按组数、金额、token、优先级设置上限。
- 通过本地配置填写自有 provider/key，或使用兼容的本地/云模型 adapter；不建设账号和密钥托管平台。
- 对低价值组、复杂组和用户指定相册设置优先级。
- 按场景统计 recommendation、attention、abstain 和用户 override。
- 支持 Windows 真机 GPU/CPU 性能基线和安装诊断。
- 导出不含原图的匿名运行报告，便于问题诊断。

### P2：后续能力

- 每次 cloud review 保存沉淀 versioned append-only 事件；初期学习采用 versioned preference profile + 相似历史 exemplars shadow，不接 live 折叠，不要求本地训练权重。
- MVP 文件闭环：导出 → 手工云训练 → 导入；不做账号/SaaS、自动上传或自动重训。默认只导出已审非 holdout 组的全量 2048 review 图、events、完整 L0/L1/DB features 和 AI receipts；原片数 TB，不做全量本地上行。
- source catalog 保存稳定 provider/asset ID 和 SHA；少量 hard-example 原片只能按 `original-request.json` 清单补包，先报告数量/bytes、显式确认、copy 前后核验 SHA。未来 Google 侧按需拉取须在 M2 现场确认 2026 API/Picker 权限，不假设能静默读全库。
- 当前约 288 对 gold pairwise/6 日期足够 baseline，不足以认证 live 折叠；阶段 2 积累千级 pair、至少 15 日期后再训练 safe-to-collapse/ranker，另建 time-based fresh holdout。现有 pair43 + large21 holdout 持续封存，bundle validator 按组与 file/SHA 硬排除。
- learner 永远无 route/execute/keeper/delete/原片写权限；导入只注册 shadow，可回滚上一版或 none。实现、命令与边界见 [LEARNING_LOOP.md](LEARNING_LOOP.md)。
- 针对舞台、多人合照、宠物、儿童动作等场景优化视觉 packet。
- 支持模型路由和成本优化，但完整图与证据审计保持不变。
- 可选局域网/自托管 VLM，前提是独立验收达到云端同类门槛。

## 9. 成功指标

### 9.1 北极星指标

**每 1,000 张照片减少的人工逐张比较次数，同时保持独特阶段和互动照片不被错误漏保。**

### 9.2 私有试点 Go/No-Go

在独立人标的疑难组验收集上：

- 至少 70% 的有效建议可被用户原样接受；
- 高置信推荐中不得出现已知独特阶段漏保；
- 相比仅分组+人工挑选，需完整逐张比较的组数降低至少 60%；
- schema/identity/evidence 验证通过率至少 95%；
- 100% 模型建议保持 review-only；
- 原图、group decision、keeper 和删除状态零非授权写入。

这些是产品准入目标，不是当前已达到的结果。

### 9.3 本地质量指标

- 每 1,000 张输入的 VLM groups、unique source photos、高分辨率 parts 与像素；
- member → representative 比例、local-resolved 比例及各 router threshold 的 Pareto；
- development human-selected decision coverage / VLM exposure recall，二张组另报本地 exact / precision / recall / F1、两张都保留的 exposure recall 与独特帧漏保；
- 本地省图造成的漏独特阶段、漏选和多留，且提供 recall-first 回退档；
- 每 100 张照片的相似组数与 VLM 调用数；
- 每组 input/output tokens、延时和估算成本；
- select / multi-select / attention / abstain 分布；
- 用户接受、修改、全保留和跳过比例；
- override 原因：表情、阶段、多人遗漏、构图、技术质量、模型误读；
- 按 single / multi / stage / action / pet / no-subject 分层表现。

## 10. 当前规模与成本基线

冻结测试集：

- 2,065 张照片；
- 510 张进入 194 个相似组，占 24.7%；
- 当前保守策略下 194 组均进入语义审阅；
- 最多 194 次单次云调用，相当于每 100 张照片约 9.4 次调用。

当前 Sonnet canary 的单组估算约 $0.05–$0.19；该价格使用显式假设费率，不等于实际账单。产品必须在扫描后、调用前显示基于真实组数和组大小的费用区间。

无 VLM 用户仍可使用完整 Core 流程；VLM 成本影响的是自动 shortlist 覆盖率，不影响本地整理和人工 review 的可用性。

冻结集单次云 judge 已完成 194/194 组：187 组结构和证据绑定通过，7 组保留原始响应并转人工；185 组返回 select、2 组 abstain。总计 3,514,159 input + 106,396 output tokens，按实验假设费率估算 $12.14。原片和冻结数据库未改，decision/keeper/delete 写入为 0。

Parent 对 12 个 validated 组做了非盲视觉抽检：10 组 shortlist 与主要理由合理；1 组推荐可接受但解释含事实错误；1 组可能过度单选并漏掉独特表情阶段。该结果说明 review shortlist 已有实用价值，也说明 schema validation 不能替代 Willy 人标，完整组图和快速改选仍是 UI 必需能力。

Willy 随后在真实 Review UI 中完成 194 组 assisted review，并统一保存自己的最终选择。按 `file_id + content_sha256` 集合直接比较，而不是使用 UI 状态标签：

- 185 个有 AI select 的组中，130 组与 Willy 完全一致，**原样接受率 70.3%**；达到首轮 70% 目标，但余量很小；
- 169/185 组至少有一张与 Willy 重合，重合率 91.4%；照片级 micro precision / recall / F1 为 85.7% / 80.7% / 83.1%；
- 2 张组完全一致率 84.0%，3 张及以上只有 41.7%；主要短板不是二选一，而是较大组的阶段覆盖和多选边界；
- Willy 在 21 组中额外保留照片、14 组中删去 AI 多留照片、20 组换选或重组；总计比 AI 多加回 50 张、删去 35 张，说明当前模型略偏向过度精简，独特阶段漏保风险高于多留风险；
- 2 个 abstain 与 7 个 failed 共占 4.6%，按设计进入人工路径。

这轮是看着 AI 建议完成的 assisted review，不是盲标，因此可以作为真实产品“建议原样接受率”和 UI 可用性基线，不能冒充独立偏好准确率。人标快照与可复现明细见 `artifacts/cloud-review-label-analysis/`。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 原片被覆盖、错删或移动错对象 | P0 硬门禁：源目录只读、输出隔离、file_id+SHA 复核、review/execute 分离、仅可恢复动作 |
| 模型漏掉旁观者闭眼或舞台小主体 | 完整组图始终输入；多人 coverage 不明时 attention/abstain |
| 模型只选技术最优图，漏独特阶段 | 可信时序、多选、不可替代阶段和独立人标验收 |
| 本地/云模型输出格式稳定但语义错误 | schema 只作为结构门禁；必须做视觉抽检和用户 override 指标 |
| VLM 成本不可控 | 一组一次调用；Budget VLM；运行前估价；可恢复缓存 |
| 大组图片/token过高 | 完整分页、硬图数/像素/文本预算；超限不抽样漏图，改为attention |
| 用户误把建议当删除动作 | review 与 execute 分离；默认无执行；可恢复目标 |
| 隐私泄露 | 当前个人使用阶段记录 provider 与发送范围即可；正式分享前再补独立隐私策略，不阻塞选片质量验证 |
| 个性偏好差异 | 第一版允许修改和全保留；记录override，不把通用模型当用户真值 |

## 13. 当前产品判断

- **作为本地分组与 review-first 工具：可用。**
- **作为语义 shortlist 产品：方向成立，但尚在冻结集和人标验证阶段。**
- **作为无人值守自动清理器：不可用，也不属于第一版目标。**
- 产品能否形成差异化，取决于是否真正降低人工比较次数，而不是相似识别本身。
